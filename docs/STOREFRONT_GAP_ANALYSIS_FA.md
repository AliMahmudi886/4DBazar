# تحلیل شکاف و MVP «غرفه 4D»

## هدف

«غرفه» صفحه عمومی و قابل اشتراک یک کسب‌وکار یا ارائه‌دهنده خدمت در بازار محلی 4D است. غرفه با حساب کاربر و فرم «پروفایل کسب‌وکار» یکی نیست و نباید فرم خصوصی اطلاعات کاربر را تکرار کند.

## وضعیت موجود

- `users` و `user_profiles` هویت، ورود، شهر اصلی و وضعیت احراز سبک را نگه می‌دارند.
- `business_profiles` اطلاعات تکمیلی کسب‌وکار را برای اعتماد و نمایش محدود نگه می‌دارد.
- `market_contents` مالک، شهر، دسته، وضعیت moderation و نوع محتوای آگهی/خدمت را دارد.
- `media_assets` و `listing_media` برای رسانه چندگانه، و صف moderation و نقش‌های admin/moderator موجود هستند.
- کمبود اصلی: موجودیت عمومی با نام، slug، وضعیت انتشار، لوگو، ساعات کاری و فهرست آگهی‌های خودش وجود ندارد.

## مرزبندی محصول

| موجودیت | کاربرد | مخاطب |
|---|---|---|
| حساب کاربر | ورود، امنیت و مالکیت | خود کاربر و API |
| پروفایل کاربر | نام، نام خانوادگی، شهر و احراز سبک | کاربر و کنترل اعتماد |
| پروفایل کسب‌وکار | اطلاعات تکمیلی مالک برای اعتماد/پروفایل | مالک و نمایش محدود |
| غرفه | صفحه عمومی برند/کسب‌وکار با slug و آگهی‌های فعال | همه بازدیدکنندگان |

## تصمیم MVP

- در MVP هر مالک حداکثر یک غرفه دارد؛ چند غرفه و staff به بعد موکول می‌شود.
- lifecycle: `draft`، `pending_review`، `active`، `suspended` و `archived`.
- ایجاد/ویرایش فقط برای مالک احراز‌شده؛ فعال‌سازی فقط با moderator/admin.
- دسته اصلی غرفه در MVP یک `category_id` از taxonomy فعلی است؛ چنددسته‌ای بعداً با جدول join اضافه می‌شود.
- لوگو و cover به `media_assets` وصل می‌شوند و مالکیت رسانه دوباره بررسی می‌شود.
- آگهی‌ها `storefront_id` nullable می‌گیرند تا انتشار بدون غرفه همچنان ممکن بماند.
- پرداخت، اشتراک پولی، دنبال‌کردن، staff، CRM، سفارش، سبد خرید، موجودی و KYC سنگین خارج از P0 هستند.

## قرارداد API پیشنهادی

- `GET /api/v1/storefronts/by-slug/:slug` عمومی و فقط برای غرفه `active`.
- `GET /api/v1/storefronts/:id` عمومی برای غرفه فعال و برای مالک/ادمین با وضعیت کامل.
- `GET /api/v1/me/storefront` غرفه مالک.
- `POST /api/v1/storefronts` ایجاد draft/pending review.
- `PATCH /api/v1/me/storefront` ویرایش مالک.
- `GET /api/v1/storefronts/:id/listings` فهرست آگهی‌های approved همان غرفه.
- `GET /api/v1/admin/storefronts` و `POST /api/v1/admin/storefronts/:id/decisions` برای moderation.

## معیار پذیرش این فاز

1. migration قابل اجرای مجدد باشد و foreign keyها از حذف مالک/دسته/شهر جلوگیری کنند.
2. slug یکتا، محدود و قابل استفاده در URL باشد.
3. API جلوی IDOR، غرفه غیر فعال و media متعلق به کاربر دیگر را بگیرد.
4. آگهی جدید و ویرایش آگهی بتواند `storefront_id` معتبر بگیرد.
5. تست‌های API برای مالک، public visibility و نقش admin/moderator اضافه شود.

## مسیر rollout

ابتدا API و migration، سپس UI مالک و صفحه عمومی، بعد پنل moderation. featureهای follow/analytics/subscription پس از smoke و بازخورد چند کسب‌وکار منتخب بررسی می‌شوند.
